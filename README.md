# K-pop Quiz

Daily K-pop quiz and puzzle games about groups and artists, in Portuguese and English. Play at <https://kpopquiz.online>.

The site has nine games: a ten-question quiz with assisted, standard, and expert modes, a grid, connections, name guess, word search, timeline, a map, a group code logic game, and a crossword. New puzzles are published every day.

Giving up in Timeline records a loss, even when the current sequence is correct. The result and share text explicitly say that the player gave up and label the numerical score as the sequence score. This distinction survives a reload; saved results from before this field was introduced retain their original submitted status. Dates and source links appear only after the round ends. Each move saves the order under the board's key (`kpop-timeline-<puzzle_id>`, with `submitted: false`), so a reload before the submit restores it; only the submit records the match, and a draft of another board or date, or with an order that is not a permutation of the board's events, is dropped. The result lists the events in the right order and, for each one, the player's position and the right position in text ("Sua posição: 4 · Posição certa: 2" / "Your position: 4 · Right position: 2"), besides the ✓/✗ mark. Each source reads as the shared citation of the "Ver fonte" panels described below, with the original revision URL and the raw locator on the link.

The daily crossword comes from a generator with a versioned schema, previous-day group exclusion and a bounded unique-assignment proof. The daily runner publishes it with a durable record of each day; a day without a proven board shows that there is no crossword instead of an earlier board. See [the CLI and benchmark guide](docs/crossword-daily.md).

Every answer comes from Wikipedia and Wikidata. A Python collector queries both APIs, records the consulted revisions in SQLite, and keeps page and entity responses as compressed JSON. Each accepted fact points to a Wikidata reference or a Wikipedia revision excerpt, and the games only use accepted facts.

The collector covers page discovery, summaries, candidate classification, and Wikidata fact extraction for accepted groups and members. It also keeps an auditable catalog of music release candidates. The catalog rejects lists, disambiguation pages, redirects, and QIDs without an accepted music type.

The map-game pilot at `/pt-br/mapa/` and `/en/map/` asks in which country the official schedule listed each date of BLACKPINK's DEADLINE WORLD TOUR. `python -m kpop_scraping.map_pilot_refresh` rebuilds `data/map-pilot/deadline-events.json`. An event enters it only when the YG schedule lists the date and city, MusicBrainz records the concert at one venue, and the venue area's current Wikidata country (P17) matches the MusicBrainz area hierarchy. The country then maps to a Natural Earth feature by Wikidata QID. A workflow runs the refresh on the first day of each month. The routes appear in the game menu and in the sitemap. [ADR-015](docs/decisions/015-contrato-de-dados-do-jogo-de-mapas.md) and [the pilot notes](docs/map-game-pilot.md) record the sources and checks.

## Requirements

- Python 3.11 or newer
- Node.js 24.15 or newer within the 24.x release line for the web interface
- Internet access to run the collector

The collector uses only the Python standard library. The daily reference date is the date in São Paulo (`America/Sao_Paulo`); without that time zone, generation stops with an error instead of falling back to UTC. Where the system has no time zone database (Windows, minimal containers), `pip install -r requirements.txt` adds `tzdata`.

Every HTTP request goes through `kpop_scraping/http_request.py`, which refuses a request without a positive timeout or without a `User-Agent` that carries a contact URL or e-mail. Retries, rate limits and `maxlag` stay in each client. `tests/test_pipeline_rules.py` fails when `urlopen` appears outside that module, or when importing a `kpop_scraping` module opens a connection or a SQLite database.

## Quick start

```bash
python3 -m venv .venv
source .venv/bin/activate
python main.py --limit 10
```

This creates `data/kpop.db`, writes snapshots to `data/raw`, and exports `data/catalog-report.csv`. Drop `--limit 10` to walk through the whole category.

The snapshot directory can live outside the database folder:

```bash
python main.py --limit 10 --database /tmp/kpop.db --raw-dir /tmp/kpop-raw
```

Use a custom identifier for recurring runs:

```bash
python main.py --user-agent "kpop-quiz/0.1 (https://your-site.example/contact)"
```

## Commands

```bash
python main.py --help
python main.py --limit 3 --database /tmp/kpop-quiz.db
python main.py --limit 3 --catalog-report /tmp/kpop-catalog.csv
python main.py --limit 45 --database /tmp/kpop.db --facts-limit 30 --facts-report /tmp/kpop-facts.csv
python main.py --limit 45 --database /tmp/kpop.db --releases --release-group-limit 10 --release-report /tmp/kpop-releases.csv
python main.py --limit 60 --database /tmp/kpop.db --releases --release-group-limit 25 --release-group-offset 25
python -m kpop_scraping.group_relevance_cli --database /tmp/kpop.db --reference-date 2026-09-21 --user-agent "kpop-quiz/0.1 (https://your-site.example/contact)"
python -m kpop_scraping.group_relevance_score_cli --database /tmp/kpop.db
python -m kpop_scraping.quiz_cli --database /tmp/kpop.db --output /tmp/questions.json --report /tmp/quiz-report.json --session-output /tmp/session.json --seed round-1 --timer-seconds 20
python -m kpop_scraping.web_publish --database /tmp/kpop.db --output-dir web/public/data --seed web-launch-v1 --timer-seconds 20
python -m kpop_scraping.web_publish --output-dir web/public/data --verify
python -m unittest discover -v
python -m compileall -q .
```

`python main.py` exits with `0` when the run finished, `75` when a transient error stopped it and `65` for any other handled failure. [Database rebuild and fallback](#database-rebuild-and-fallback) lists what each code means for the daily job. When Wikipedia or Wikidata answers `maxlag`, the run waits out the lag for up to 15 minutes in total; `MAXLAG_BUDGET_SECONDS` changes that budget (`0` gives up on the first `maxlag`).

## Web interface

The static interface uses Astro and Preact. The production build produces the `/pt-br/` and `/en/` routes at the site root. Opening `/` renders the Portuguese quiz directly and uses `/pt-br/` as its canonical URL. The site is published on Cloudflare Pages at <https://kpopquiz.online> (with `kpopquiz.pages.dev` as the platform URL). A push to the `dev` branch deploys a staging build to GitHub Pages at <https://pedrosatin.github.io/kpop-quiz/>. The staging workflow sets `ASTRO_SITE` and `ASTRO_BASE`, so page and asset URLs start with `/kpop-quiz/`. The browser validates the manifest, the SHA-256, and the session contract before starting the quiz.

```bash
cd web
npm ci
npm test
npm run build
ASTRO_SITE=https://pedrosatin.github.io ASTRO_BASE=/kpop-quiz npm run build  # staging build under /kpop-quiz/
npm run playwright:install   # Chromium once per machine
npm run test:e2e             # builds via pretest, then full Chromium suite on dist/
npm run test:e2e:ci          # full Chromium suite on an existing dist/ (no rebuild)
npm run test:e2e:boot        # Chromium boot smoke only
npm run test:e2e:playthrough # Chromium pt-BR playthroughs only
npm run test:e2e:nightly     # Firefox + WebKit boot smoke
npm run test:e2e:staging     # full Chromium suite against staging
npm run test:e2e:prod        # full Chromium suite against https://kpopquiz.online
```

### End-to-end tests

On mobile, the Quiz keeps a scrollable question area above its sticky actions.
Long feedback and source details scroll independently without covering answers.
`cd web && npx playwright test --config playwright.quiz-layout.config.ts` checks
PT/EN at 360, 390 and 1280 pixels with consent open and rejected. It creates a
separate local build with a fictitious GA4 ID and blocks external browser requests;
it does not require analytics credentials or replace the production artifact.

Playwright's Chromium gate runs boot smoke plus pt-BR playthroughs. The gate covers game routes and privacy in pt-BR and EN.

Boot for games checks HTTP 200, the shell, a setup or start CTA, and a visible board (or Grid missing+retry when the daily artifact is absent). Privacy boot checks the shell and privacy content only.

Playthroughs are pt-BR only. They drive each of the six board-and-question games to `game-result`. Connections and Name Guess lose or exhaust wrong guesses. Word Search completes from daily JSON coordinates. Quiz and Map take any-answer paths through to the end. Timeline submits the default order. Grid fills when the artifact exists, else uses the missing+retry UI. Both specs seed `kpop-quiz-consent` to `rejected` so the GA4 banner does not block the suite. The group code game has its own spec, `code.spec.ts`, in both languages.

Locally, `npm run test:e2e` runs `pretest:e2e` first, which builds `dist/`. CI already has a build, so the workflows call `npm run test:e2e:ci` against that artifact. Do not use `test:e2e` in CI, because pretest would rebuild. Narrower scripts are `test:e2e:boot` and `test:e2e:playthrough`.

The Code feedback spec has three build contracts selected with `CODE_FEEDBACK_ENV`: `banner` requires the real consent island and runs open/rejected banner cases; `root` requires no GA4 or banner and, by default, no Cloudflare beacon; `staging` requires a path prefix, no analytics or banner, and `noindex`. All three exercise PT/EN at 360, 390 and 1280 pixels. A mismatched build fails its contract assertions.

The default is `staging` when `ASTRO_BASE` or `BASE_URL` has a prefix, otherwise `root`. CI runs all three contracts with dummy IDs where needed, without retries or secrets. Production and staging workflows select the contract for their built artifact. Production also declares `CODE_FEEDBACK_CF_BEACON=true` when its existing build includes the independent Cloudflare beacon; staging always forbids it.

For local reproduction, run each build and its browser check sequentially from `web/`. An empty ID removes analytics; a dummy ID renders the real banner only at the root. External requests in this spec are aborted unless their exact origin matches the target, including scheme and port. The known puzzle is intercepted only at the target's prefixed data paths.

The grid maps a pointer to a cell from its coordinates, so a touch in the 2px gap goes to the nearest cell and a tap at the center of a cell marks that cell. A drag keeps a straight line from the cell where it began: the line follows the nearest of the eight directions and ends at the cell nearest to the finger's projection on it, so the finger can stray sideways, and a drag lifted past the edge stops at the edge. A press stays a tap until the finger moves half a cell from the point where it went down, so a tap near a gap that trembles across it marks one cell. While a finger is down, a second one is ignored, and a press the browser takes over before any drag leaves the selection as it was. Two taps work as well as a drag, and the bar spells out the selected letters. A smaller grid on phones would need a separate puzzle per screen size from the generator, so players of the same day would not share a board.

In the grid the `.game-actions` bar sits under the board (beside it from 60rem, with the message at the top and the counters at its foot) and holds a two-line message next to the counters ("9 palpites restantes" / "9 guesses left" and "0 de 9 casas certas" / "0 of 9 squares correct"). The message is the live region: the instructions at first, then the verdict of the last guess with the group's name ("Certa: TWICE." / "Correct: TWICE.", "Errada: SHINee." / "Wrong: SHINee."), followed by the counters for screen readers. The board never moves, and the headers, the nine cells and the bar fit at 390x844, 768x1024, 1362x940 and 1440x900; from 60rem the cells grow with the viewport height from 5rem up to 6.5rem. The group picker is a modal dialog: Tab stays inside it, Escape and Close return focus to the cell that opened it, and on phones it follows the visual viewport so the search field and about five groups stay above the keyboard. The search ignores accents, case, spaces and punctuation, so "stray kids", "straykids" and "Stray-Kids" find Stray Kids and "gidle" finds I-dle. It also finds a group by its other names: grids published from now on carry, per candidate, `aliases`, the group's labels in other languages, alternative labels, native names and romanizations from the Wikidata entity snapshot of the dataset (`entity_aliases`), minus the names already shown. A match through an alias shows that alias beside the group's name ("Girls' Generation SNSD"). Whole names come first, then names that start with the search, then the rest. Grids published before the field have no aliases and still load. A guess is spent only on a group the player chose: a tap, or Enter on the group reached with the arrow keys or named by the search (the only match, unless only part of an alias matched it; the first whose shown name is the whole search; or the one group with an alias that is). Part of an alias never names a group: "singer", inside the Wikidata alias "South Korean singer" of Blackpink, lists Blackpink but Enter sends nothing. Enter with an empty search sends nothing. The picker marks in words the groups already tried in this cell ("Já tentado aqui" / "Already tried here") and those used in another cell ("Usado em outra casa" / "Used in another square"); picking a group already refused in this cell closes the picker, spends no guess and says so in the bar ("Já tentado aqui: BTS. Nenhum palpite gasto." / "Already tried here: BTS. No guess spent."). After a guess focus goes to the same cell when it is still open, or to the next empty cell after a right guess. A solved cell stays focusable with `aria-disabled`, so the arrow keys still walk through it, and for 300ms after a guess the board ignores taps and clicks, so a double tap on a group does not open the cell under it; Enter and Space still open the focused cell, and a held key does not. The grid is now saved per grid in `localStorage` under `kpop-grid-<grid_id>` after each guess and restored on reload. The save keeps the QIDs of the right groups and, per cell, of the last wrong group (`lastAttemptId`) and every wrong group tried (`triedIds`), so the names follow the page's language; a save from before `triedIds` counts its `lastAttemptId` as the one group tried. An untouched board is not saved, and a save that names a group outside the pool or one the cell does not accept, or counts more groups than guesses, is dropped. When the game ends the result replaces the counters in the bar: the title (described by the "8 de 9 casas certas com 9 palpites" / "8 of 9 squares correct in 9 guesses" summary, which starts with the verdict of the last guess when the game ends during the visit), Share and a "Ver fonte" / "Show source" toggle (labelled "Ocultar fonte" / "Hide source" while open), with the high-contrast option under them. Below 60rem, at the end the icon moves beside the name, names keep two lines and the rows get shorter (3.5rem from 30rem); on phones the category tags and the check marks of right cells hide and the rows shrink toward the 44px touch target, so the finished board stays above the taller bar. A wrong cell keeps its cross and strike-through. The panel lists, for each cell, the player's answer, the accepted groups and one line per group and cited revision with every location in the source ("Local na fonte" / "Location in source") in words, such as "caracteres 140 a 148 do resumo" / "extract characters 140–148", with the raw locator in the tooltip; while it is open the bar stops being sticky. Share opens the system share sheet where there is one and otherwise copies the text, which ends with the game link; if neither works, the live region says so and the text shows in a read-only field to copy by hand. The result buttons, "Ver fonte" included, ignore activation for 300ms and held keys. Focus moves to the result title only when the game ends during the visit; a finished game restored from storage does not take focus, and it is counted in the statistics once, on the first load that finds it uncounted.

In the map quiz the question sits over the map, and the `.game-actions` bar holds the selection controls, the verdict and Next. On wide screens a tap or click on the map, and anywhere a tap on a country in the list, only selects; "Responder" / "Answer" commits the attempt once and locks the choice. Map, list and select share the same pending selection, so a player can swap countries before sending. From 60rem wide the round's 14 countries sit beside the map in two columns of 44px buttons under a visible "Países desta rodada" / "Countries in this round" heading, sorted by name in the page's language; at 1440x900 the map keeps 644 of the 760px it had alone, and the list ends above the bar. The bar keeps Answer on wide screens and hides the select there. Below 60rem the list did not fit above the bar, so the same countries are a select in the bar with Answer, and Next takes that button's place after the answer. There the map is a 5:3 box capped by `--play-max-h` (298x170px at 360x740 and 328x197px at 390x844, where the world alone was a 298x119 and a 328x131 strip), and its first tap zooms into the tapped region at 2px per map unit instead of selecting; "Mapa inteiro" / "Whole map", in a strip under the zoomed map where it covers no target, goes back and moves focus to the map, and a hint over the map says a tap zooms. Only a finger, a pen or a mouse zooms: a click from a screen reader or voice control selects the country, and for 300ms after the zoom a tap selects nothing, so a double tap does not pick a second country. In the zoomed map every country of the round has a 44px round target centered on the bounding box of its largest landmass, drawn as a ring around the countries smaller than that (Singapore, Taiwan and South Korea); the closest targets, the Philippines and Taiwan, keep 26.9 units (54px) between centers, and a unit test fails if a data refresh brings two countries of the round closer than one target. On the whole map a country under 8px gets a dot. Every date starts on the whole map, and an answer whose country is outside the zoomed view, or Tab to such a country, goes back to it. A country takes the selection color on hover only on devices that hover, and keyboard focus uses `:focus-visible`, so a tap no longer leaves a country looking picked on the next date. Answer stays in the Tab order with `aria-disabled` until a country is picked; pressed before that, the live region says "Escolha um país primeiro." / "Pick a country first.". Tab reaches the highlighted map countries; Enter or Space selects, and Answer submits. After an answer the bar keeps only Next ("Desistir" / "Give up" returns on the next date), and its live region shows the verdict, "Sua resposta" / "Your answer" when it is wrong, the correct country and the links to the YG schedule and MusicBrainz. At 420px and below the schedule notice beside the links is visually hidden but stays in the live region for screen readers. Next gets focus and ignores activation for 300ms and a held Enter, so a double tap on Answer does not skip the verdict. A pending selection is not saved; only committed answers and the date on screen resume after a reload. The round date is the date in São Paulo (America/Sao_Paulo), the same one the daily games use to turn the day, so the round and its save change at midnight there. Progress is saved per round date in `localStorage` under `kpop-map-<YYYY-MM-DD>` as `{ events, answers, index }`: the MusicBrainz event MBIDs of the round, the map feature picked for each answered date and the date on screen. A save for other events (after a data refresh), with a feature outside the round's countries or with counts that play cannot reach is dropped, an untouched round is not saved, and loading the game removes the saves of other dates. A reload resumes the date on screen, answered or not, or the result, without moving focus. When the round ends the map shows the round's countries and the result replaces Next in the bar: the title (described by the "7 de 10 certas." / "7 of 10 right." summary), Share and a "Ver fonte" / "Show source" toggle (labelled "Ocultar fonte" / "Hide source" while open). The panel lists each date with the correct country, the player's answer, the YG schedule link with the location in the source ("Local na fonte: GOYANG, GOYANG STADIUM", the raw locator in the tooltip), the MusicBrainz event, the Wikidata QID and revision that gave the country of the venue's area (a link to that revision) and the date checked; while it is open the bar stops being sticky. Share opens the system share sheet where there is one and otherwise copies a localized header (`Mapa de K-pop <date>` / `K-pop Map <date>`), the score, one square per date (🟩 right, ⬛ wrong, as in Adivinhe) and the game link; if neither works, the live region says so and the text shows in a read-only field to copy by hand. The result buttons ignore activation for 300ms and held keys. Focus moves to the result title only when the round ends during the visit.

Player statistics stay in `localStorage` under `kpop-player-stats-v1`. The overall streak counts consecutive days with at least one daily challenge finished, win or lose. Each game's streak counts consecutive daily wins of that game, and a loss sets it back to zero. A general Quiz game adds to the played and won counters and leaves both streaks alone, and a daily challenge counts once. Daily games are recorded under the challenge's `reference_date`, so the day turns at midnight in São Paulo on any device, and a record dated before the last one changes no streak. The Map records a finished daily round once, under the round date, and counts it as a win when at least half the dates are right and the player did not give up; a round saved as a replay is not counted. The statistics window shows the streak rule for the tab on screen and, on each game tab, what counts as a win in that game, in Portuguese and English: at least half right in the Quiz (5 of 10) and the Map (5 of 10 dates), at least 5 of the 9 squares in the grid, the 4 categories before the fourth mistake in Connections, the name in up to 6 guesses, every name in Word Search, every event in order in Timeline (a give-up in the grid, Word Search, Timeline or the Map is not a win), the code in up to 10 tries, and the crossword solved with "Verificar respostas" / "Check answers" without "Revelar respostas" / "Reveal answers". The Name Guess distribution ends with an "X" bar for losses, read as `played - won`, so the stored format stays the same. Opened from a game page, the window starts on that game's tab; on close (Esc, the close button or the backdrop) focus goes back to the stats button, even when the click did not focus it, as a tap in Safari does not. A daily match is identified by the game and its `reference_date` ([ADR 030](docs/decisions/030-partida-diaria-por-jogo-e-data.md)): a board republished for the same date (`--regenerate`, a revalidated grid, a crossword generated again on promotion) is the same match. A player who finished the date sees "Desafio de hoje concluído" / "Today's challenge is done" with `DailyNext` instead of the new board, and the daily Quiz setup says the day's round no longer counts. A match counted before the change, under the board's `puzzle_id` or the crossword's `dataset_version`, is still recognized. Progress stays keyed by the board, so a save of another board never resumes; the group code save keeps its `puzzle_id` for this. The daily analytics flag (`daily`) reads the same identity. When neither `data/` nor `data/next/` has today's board (the date in São Paulo), Connections, Name Guess, Word Search, Timeline, the group code and the daily Quiz serve the latest board they have and say so above the game: "Este é o desafio de <data>. O de hoje ainda não saiu." / "This is the challenge from <date>. Today's is not out yet." That round records nothing in the statistics and sends `daily: "no"`. The loader decides this once, when it serves the board (`noteDailyBoard` and `staleDailyDate` in `web/src/data/daily-artifact.ts`), so a board loaded before midnight still counts for its date. The grid and the crossword keep their own rules. A day without a publication still breaks the streak: protecting it needs a publication history per game that the web can read.

The result of every daily game (the daily Quiz, Grid, Connections, Guess, Word Search, Map, Timeline, Code and Crossword) ends with `DailyNext` (`web/src/components/Results/DailyNext.tsx`) instead of "Jogar novamente" / "Play again", which stays only in the general Quiz. It shows "Novo desafio em HH:MM:SS" / "New puzzle in HH:MM:SS", counted to the next midnight in São Paulo and updated every second with `aria-live="off"`; at zero it offers a reload. Beside it, "Próximo: <game> →" / "Next: <game> →" links the first game, in tab order, not finished today (the Quiz link opens `?theme=daily`); when every game is finished, a sentence says so and there is no link. The game tabs (`GameNav`) mark each game finished today with a ✓ and the visually hidden text "concluído hoje" / "done today". Both read `web/src/lib/daily-progress.ts`: a game is finished today when its stats keep today as `lastPlayedDate` (a daily match, won or lost), and the map when the save of the day shows the result. Clock and storage are read only after mounting, so the server HTML carries neither.

`web_publish` generates ten-question sessions in Portuguese and English for the assisted, standard, and expert modes. The files land in `web/public/data`. Each filename includes its SHA-256, and the publisher swaps `manifest-v2.json` only after validating and writing all six sessions. `manifest.json` and the v1 sessions stay published during the transition. The deploy workflow verifies the v2 artifacts before the build.

## Privacy, analytics, and indexing

Production pages include the Cloudflare Web Analytics beacon only when the `PUBLIC_CF_BEACON_TOKEN` build secret is set; the staging build never includes it. What is collected: page URL, referrer, and coarse device/geo aggregates in the Cloudflare dashboard. What is not collected: no cookies, no personal data, no cross-site tracking.

Google Analytics 4 loads only after explicit opt-in through the consent banner, which appears solely in production builds with the `PUBLIC_GA4_ID` build secret set. Accepting stores `accepted` in localStorage (`kpop-quiz-consent`) and loads `gtag`; rejecting stores `rejected` and nothing from Google loads. The "Preferências de privacidade" button in the footer remains available after either choice. It reopens the banner, and choosing "Recusar Google Analytics" disables future GA4 measurement in the current visit and later visits. At 360x740, 390x664 and 390x844 with the default font size, the open banner is at most 130px tall: one sentence that names Cloudflare's cookieless measurement and asks about Google Analytics cookies and identifiers for audience statistics, the privacy policy link, and "Recusar"/"Aceitar Google Analytics" side by side with the same style. It stays fixed at the bottom and publishes its height as `--consent-banner-height`, so the sticky action bars sit above it and the boards subtract it. The page reserves the same height at its end, and keyboard focus scrolls clear of the banner. Keyboard focus also stops above the sticky action bar. The bar's height is `--game-actions-height`, described with `components.css` in the table above. The dual setup is recorded in [ADR 017](docs/decisions/017-web-analytics.md). Until each secret is configured, production builds ship without that beacon by design.

For search and LLM indexing, production serves `sitemap.xml` (18 canonical routes for nine games in both languages, each with `xhtml:link` language alternates and English `x-default`), a `404.html` page with `noindex` that Cloudflare Pages returns with HTTP 404 for unknown paths, an environment-aware `robots.txt` (staging answers `Disallow: /`), canonical URLs with `hreflang` (`pt-BR`/`en`/`x-default`), per-route titles and descriptions, Open Graph and Twitter tags with a 1200x630 card per route (`summary_large_image`, PNGs in `web/public/og/` regenerated by `npm run og:generate`), and `llms.txt` with Markdown versions of each route under `web/public/llms/`. JSON data files under `/data/` are excluded from the sitemap and carry `X-Robots-Tag: noindex`; `robots.txt` leaves them crawlable so Google can render the game islands and read that header. Every game route has a K-pop H1 and a static block under the game (`GameAbout.astro`, copy in `web/src/i18n/game-about.ts`) with How to play, data sources and FAQ sections. Every shared result ends with the production URL of the game in the player's language, tagged `utm_source=share&utm_medium=social&utm_campaign=<game>`; the share sheet and the clipboard both get the whole text with the link on the last line, and the share sheet receives no separate `url` field. Share headers follow the page language (for example `Grade de K-pop` / `K-pop Grid`, `Conexões de K-pop` / `K-pop Connections`, `Caça-palavras de K-pop` / `K-pop Word Search`, `Cruzadinha de K-pop` / `K-pop Crossword`, `Código de grupos de K-pop` / `K-pop Code`); the body keeps the score, date, emoji grid and the link, without spoilers. Player-facing group labels keep the spelling the source published: no casing is inferred from `canonical_name`, because neither side is a proven authority (`ATEEZ`/`Ateez`, `tripleS`/`TripleS` and `izna`/`Izna` differ only by case and stay as published). They strip a trailing Wikipedia-style disambiguator such as `(grupo)`, `(banda)`, `(grupo musical)`, `(band)` or `(girl group)` only when that short form stays unique among the labels shown together. The page does that for each set it shows at once: the Grid pool, the Connections items, the Word Search words and the Group code symbols; a label shown alone is never stripped. A spelling changes only through an entry in `web/src/data/display-label-overrides.json`, read by the page; an entry names the QID and locale, the exact published label it replaces and evidence with a pinned revision, and it stops applying if the published label changes. The only entry is `shinee` (pt-BR, Q269836) → `SHINee`, backed by the English Wikipedia lead of revision 1374819748 ("stylized as SHINee") and the Wikidata revision 2550137162, whose `en` label is `SHINee`. No generator cleans labels: every artifact publishes them as collected, so `dataset_version`, `puzzle_id`, `grid_id` and the code-groups draw do not depend on display cleanup. Name Guess shows one target, so no peers prove a short form unique: its result keeps the published label (`Tahiti (banda)`) and applies only reviewed overrides, as for any label shown alone. Its `puzzle_id`, the key of the browser saves, is the SHA-256 of the canonical payload without `puzzle_id`; `validate_name_guess_puzzle` recomputes it, so editing a label or any other published field without sealing a new id is rejected. Every name-guess artifact in the repository history already satisfies this, so older artifacts, their ids and their saves are unaffected. QIDs, answer keys and alias search stay on the raw published names; Boyfriend/`BF` stay as published when the strings differ. After a production deploy triggered by a code change, `pages.yml` sends the sitemap URLs to IndexNow with the public key in `web/public/<key>.txt`; a failed ping only logs a warning. The strategy is recorded in [ADR 018](docs/decisions/018-seo-llm-indexing.md), [ADR 020](docs/decisions/020-pagina-404-e-sitemap.md), [ADR 021](docs/decisions/021-cartoes-og-e-link-no-compartilhamento.md) and [ADR 022](docs/decisions/022-renderizacao-e-texto-indexavel.md). The quiz landing pages also render a linked guide to all nine games and explain quiz settings and source review. Each page's `x-default` points to its English equivalent. The sitemap omits `lastmod` until reliable dates of significant modification are available for each route; the build date does not establish when a page's content last changed. Game pages also link to two related games with descriptive anchors. `WebApplication` JSON-LD identifies each game by its canonical URL and page language; quiz landing pages declare the site name through `WebSite` JSON-LD, including at the domain root. Search Console verification and sitemap submission remain operator steps.

The daily cycle is automated by the unified runner and the `daily-puzzles-cron.yml` workflow. The cron job rebuilds the database from Wikipedia and Wikidata with incremental caching, generates the daily games (`grid.daily.json`, `connections.daily.json`, `name-guess.daily.json`, `word-search.daily.json`, `timeline.daily.json`, `code-groups.daily.json`, `crossword.daily.json`, and the daily sessions for both languages), validates each artifact against its matching schema in a temporary directory, and publishes by atomic swap only when every check passes. A game whose generator fails is left out of the day and the other games still publish; see [Partial publication](#partial-publication). If the rebuild does not finish, a separate step deletes the raw snapshots written by the failed attempts, restores the cached database, and the workflow publishes the day's puzzles from it. A transient error (usually Wikidata answering `maxlag`) gets 3 attempts, 10 minutes apart, and any other failure gets one attempt; see [Database rebuild and fallback](#database-rebuild-and-fallback). If the grid generator cannot fill a 3x3, the runner keeps the previous grid when it still passes validation and every answer is still admitted by its row and column criteria under the current member-count policy; when the previous grid is invalid, no longer admitted or absent, the day publishes without `grid.daily.json`, the grid page reports the artifact as missing, and the workflow shows a warning in the run summary. The group code pilot follows the partial publish policy: when its generation fails, the day still publishes the other games without `code-groups.daily.json`, the result records the absence (and the error) in `code_groups_skipped`, the workflow shows a warning in the run summary, and no previous day's pilot is reused because the puzzle is date-derived. The crossword follows the same partial publish policy and never reuses an earlier board. No group may repeat on consecutive days, so every set also publishes `crossword-publication.<date>.json` (`kpop-crossword-publication-v1`: state `played` or `omitted`, QIDs, artifact checksum, fact base identity and the history consumed); the records accumulate in `web/public/data/` and the next day is generated from the confirmed record of the day before. A missing record, an unreadable fact base or an exhausted generator omits only the crossword (`crossword_skipped`, warning `Daily crossword omitted`); an exhausted generator still publishes its `status: omitted` envelope, and the page says there is no crossword that day. A promoted day whose board was prepared from a history the confirmed previous day no longer matches is generated again (`crossword_confirmed`). Inside a run, the runner's own verify step accepts a published set without the grid, the group code or the crossword file and validates each one when it is present; strict callers can require them with `--require-grid` / `--require-code-groups` / `--require-crossword`. The deploy gate is stricter. `npm --prefix web run artifacts:verify` runs in the cron before the commit, and the Cloudflare Pages and staging workflows run the same command line. It checks `web/public/data/` and, when it holds a manifest or a `daily-set.json`, `web/public/data/next/`, the set the site serves between midnight in Sao Paulo and the promotion. In both directories it requires the grid, connections, name guess, word search and timeline files, unless the set's `daily-set.json` lists the game as omitted. A missing grid also passes when the day's `grid-publication.<date>.json` (dated by `daily-set.json`, or by `connections.daily.json` in a set older than that record) has `grid_id: null`. The runner writes that record when it publishes a day without a grid (`grid_skipped`), so the gate agrees with that fallback instead of blocking the deploy, and a grid lost any other way still fails. The group code and the crossword keep the partial publish policy: validated when present. A failure names the directory and, when one file is at fault, the file path. Grid validation also rejects an intersection grid whose row and column axes share a criterion category, the rule the generator has enforced since #87. The pre-fix `next/` set published before that merge was removed from the repository, so the day is generated again under the rule instead of being served or promoted from the stale copy. The workflow runs at 15:00 UTC with `--ahead`, which also publishes the next day's set under `web/public/data/next/`. After midnight in Sao Paulo, the web loaders read `next/` when the main artifact is from an earlier day, so a late run does not leave the site on yesterday's puzzles. The next run promotes `next/` without generating it again, and a day that is already published is kept unless `--regenerate` is passed, so every player gets the same puzzle for a date. The exception is a kept or promoted grid whose answers the current policy no longer admits: the runner generates the grid again for that date (a new `grid_id`, reported in `grid_revalidated`), or removes it when generation fails, and leaves the day's other files untouched. The cron enforces that rule before the upload with `python -m kpop_scraping.board_swap_gate`, which runs after `artifacts:verify` and reads the declarations from the file the generation step writes with `--board-swaps-file` (`regenerate` plus the `board_swaps` of the result). For every date the working tree publishes in `web/public/data`, it compares the identity of each board (the daily quiz sessions, `grid_id`, the `puzzle_id` of Connections, Name Guess, Word Search, Timeline and the group code, the crossword `dataset_version`) with the same date in the base commit, whether the base served it from `web/public/data` or, between midnight in Sao Paulo and the promotion, from `web/public/data/next/`. A board may change only when the run was started with `--regenerate` or the runner declared the swap (`grid_revalidated`, or a crossword generated again on promotion); the log shows each accepted swap. Any other change fails the step with the game and the date, and a missing declaration file or an unknown base commit fails it too. Changes that only touch `next/`, a day published for the first time and a new day do not count, because no earlier set of that date was served. A kept or promoted connections board is also checked against the database for a single solution (`connections_partition` in the result): a board that admits a second partition among the criteria's other members stops the run before it is kept or installed, with a message that points at `--regenerate`; without a database the check is recorded as not run, with a warning. When the generator builds a new board, an "N members" category also needs every one of the other 12 items ruled out of N by the data: a group whose member list is complete must have another count, and any other group needs bounds that exclude N, from its loaded members (lower) to its current member statements, conflicting and rejected ones included (upper). A group with no current member statement has no upper bound, so it counts as possibly N and the board is refused (the 2026-11-11 board paired "3 members" with BigBang and Super Junior-L.S.S.). A kept or promoted board is not checked for this rule, since it may already have been played, and `web_publish --verify` cannot check it, since the artifact does not carry the other items' member counts. The connections generator draws the sets of four criteria, and the quads of groups inside each set, one at a time in an order fixed by the seed (`kpop_scraping/lazy_order.py`), so its time and memory grow with the number of draws. A criterion of 300 groups takes about a millisecond, where listing every quad of 100 groups took 15 s. Each board has a budget of 10,000 steps (`MAX_SEARCH_STEPS`); a step is a set of criteria drawn, a quad drawn at any level of the search, or a uniqueness check. On the catalog of 2026-11-13 the daily seeds of 365 dates used 6 to 1,590 steps. A board over the budget fails with a `ValueError` that names the seed, the limit and the steps spent of each kind; the worst case measured, where every board splits in more than one way, reached it in about 21 s on a laptop in the case measured, and the cost of a uniqueness check grows when the criteria overlap more. This order replaced a shuffle of complete lists in November 2026 and gives other boards for the same date. A day already served, in `web/public/data` or in `next/`, is kept. The set of the next day under `next/`, which the runner generates again on each run, comes out in the new order, and a date generated again with `--regenerate` gets the new board ([ADR 035](docs/decisions/035-busca-preguicosa-da-connections.md)). Each game's seed is derived from the date (`kpop-{game}-daily-{YYYY-MM-DD}`), so the same date and database produce identical bytes. The word search schema validation, which the runner, `publish` and the deploy gate all call, refuses a grid where a word occurs outside its declared coordinates, in any of the eight directions, reversed reading included; a palindrome may also read back along its own line. In the word search, each word's clue cites one audited fact that sets it apart from the other theme words (birth year, formation year, record label, or another group), and its evidence is published with the word; words without such a fact have no clue. The rule is in [ADR 011](docs/decisions/011-mecanica-caca-palavras.md). The seed also draws the word search theme. When that theme cannot be placed within the fixed budget, as with a label whose names include one inside another (`VIXX` inside `VIXXLR`), the generator tries the other themes in an order fixed by the seed and the theme ids, under the same budget and the same validators that forbid any word outside its declared position, and publishes the first that fits. A date whose drawn theme fits keeps its bytes and `puzzle_id`. A replaced theme is not dropped from the draw: the runner logs the abandoned and the published theme ids, returns them in `word_search_fallback` (for the day and for `next`), and the workflow shows the `Word search theme replaced` warning in the run summary. When no theme fits, the error names every theme tried and the day publishes without the word search. The same flow runs locally with `python -m kpop_scraping.daily_puzzles_cli --database data/kpop.db --output-dir web/public/data`, with standalone verification via `--verify`.

A new run updates each page by the combination of provider, language, and `pageid`. `collection_runs` records success or failure. `source_pages` holds the latest state, `source_revisions` points to each snapshot and its SHA-256, and `collection_run_revisions` records which revisions each run used. A snapshot that a database references never changes, and reading it checks that SHA-256. When a run finds a file with different content at a path its database does not reference yet, it moves that file to `.orphans/` inside the snapshot directory as `<name>.<sha256 of the file>.orphan` and writes the new snapshot. Another database that shares the directory and referenced the old bytes can recover them from there. `catalog_entries` holds one decision per page. A new revision, or a change to the metadata the classifier uses, returns the page to the `candidate` state.

The pipeline stores no Wikipedia page whose intro extract is larger than 32 KiB in UTF-8 (`MAX_EXTRACT_BYTES` in `kpop_scraping/mediawiki.py`). The evidence rules run regexes and sentence loops over the whole extract, so its size bounds their cost; the largest extract in the maintainers' local database was 3.7 KB in November 2026. The run continues without the page and records `page_extract_oversize`: in `collection_issues` for a group page, in `release_source_pages` for a release page, and in `person_source_pages` for a person page. No snapshot is written for that revision, and a group that already had a revision in the catalog keeps it.

TextExtracts renders the extract from the current parse of a revision, so an edit to a transcluded template or a parser deployment can change it while the `revid` stays the same. When a run fetches a stored revision whose snapshot passes its SHA-256 check but whose extract differs, the page keeps the stored snapshot and is skipped. The run writes no snapshot, page row, run link or catalog change for it, records `extract_drift` in `collection_issues` with the revision, the language and the SHA-256 of both extracts, and goes on with exit code `0`. Evidence that cites the stored snapshot stays as it was, and so do the `accepted` rows of a release page in `release_source_pages` and of a person page in `person_source_pages`, which point at the stored revision. The page stays frozen until it gets a new revision. The CLI writes one `WARNING: extract of <language> page <pageid> revision <revid> changed without a new revision; kept the stored snapshot (...)` line per page to stderr, prints `::warning title=Extract changed without a new revision::` with the language, `pageid` and `revid` of up to 20 pages under GitHub Actions, and adds `Extract drift: <n> page(s) kept the stored snapshot of an unchanged revision` to the summary. No page title or extract text reaches the warning. A snapshot file that cannot be read, fails its SHA-256 or holds another revision still fails the run with `SnapshotIntegrityError` and exit code `65`. [ADR 036](docs/decisions/036-extract-divergente-em-quarentena.md) records the decision.

The standalone grid CLI generates a diagnostic artifact, for example `python -m kpop_scraping.grid_cli --database <database-copy> --date YYYY-MM-DD --output <review-directory>/grid.daily.json`. Publish daily corrections through the daily runner so the grid and its publication metadata stay consistent; replacing only the deployed grid JSON is insufficient.

A database collected before infobox evidence was added needs fact extraction again; applying the database migration alone does not add that evidence. If generation still fails, the error reports the number of groups with sourced formation dates, record labels, and complete member lists. Changing the seed cannot repair missing evidence.

New daily publications include `grid-publication.YYYY-MM-DD.json`, a separate `kpop-grid-publication-v1` contract described in [ADR 008](docs/decisions/008-grade-de-intersecoes.md) and `schemas/grid-publication-v1.json`. It binds the publication date to the authorized grid hash and grid date, or declares the grid unavailable with null values. Its cumulative `replaces` array identifies rejected versions of the same day's challenge. The runner writes an unavailable record before correcting a published grid and synchronizes the grid and metadata in `next/` after promotion. Other games keep their bytes. The loader requests date-specific metadata with `cache: no-store`, rejects mismatched or invalid records, and does not recover a rejected grid through `next/` when generation fails. Rejection is recorded at the artifact's original date before removal, even when the publication date is later. Origin records and cumulative rejection history survive rotation and promotion of `next/`. When considering a prior-day artifact, the loader checks both the publication permission and the origin record. A later reuse permission cannot override an origin rejection or authorize a different hash/date pair, so rejected bytes served by a cache remain unusable. Legacy publications without metadata remain readable. The PT/EN interface labels a corrected challenge and explains that previous-version progress cannot resume. The notice persists on reload; new guesses resume under the corrected hash. Ordinary reloads and new days do not announce a correction. Saves are never migrated between grid identities. Production data must be regenerated and deployed before this policy affects the public site.

The `generate_daily_grid()` helper defaults to the same Sao Paulo reference date as the publisher. With the date-derived seed, two consecutive dates never get the same six criteria, whichever axis each one is on. A date with an even ordinal (`date.toordinal()`) keeps what its seed draws. A date with an odd ordinal skips the criteria the seeds of the day before and the day after draw, so the rule reads no publication history. When those are the only solvable criteria, generation of the odd date fails with `ValueError` and the runner's usual fallback applies: it keeps the previous grid with the `Daily grid not updated` warning, or publishes the day without a grid. An explicit `seed` turns the rule off. The guarantee holds for one fact base. Each day is generated from the database of its own run, so a refresh that changes what a neighbour's seed draws can still produce a repeat. [ADR 008](docs/decisions/008-grade-de-intersecoes.md) records the decision and the measurement.

The grid generator never lists the pairs of axes. The decade and member-count criteria are fixed lists in the code (4 and 12); the facts add one record label criterion per label, with no limit, and the search uses those with at least three groups. For each choice of the fixed criteria in a category partition, the generator keeps the record labels whose groups meet every criterion of the other axis, so each subset of them completes a pair whose nine cells all have a group. It draws those pairs one at a time, in an order fixed by the seed (`shuffled_blocks` in `kpop_scraping/lazy_order.py`), so every solvable pair keeps the same chance of being chosen, and a pair skipped for a neighbouring day still uses its draw. The mixed-axis fallback draws its row axes the same way. One selection of axes has a budget of 20,000 steps (`MAX_AXIS_SEARCH_STEPS`); a step is a curated pair drawn, a fallback row axis drawn, or a fallback column triple tested. On a copy of the 2026-10-19 database with the formation years of ADR 029, the daily seeds of 365 dates used 1 to 4 steps per selection, and a selection that avoided every solvable set used 8,518. A selection over the budget fails with a `ValueError` that names the seed, the limit and the steps spent of each kind, and the runner handles it like any other grid failure. With 100 record labels of three groups and the 12 member counts, a selection ends in about half a second, where listing the 116 million pairs stopped with `MemoryError` under a 2 GiB cap. This order replaced a shuffle of the complete pair list in November 2026 and gives other grids for the same dates. A day already served, in `web/public/data` or promoted from `next/`, keeps its grid; the next day under `next/`, which the runner generates again on each run, and a date generated again with `--regenerate` get the new order ([ADR 038](docs/decisions/038-busca-preguicosa-dos-eixos-da-grade.md)).

The grid counts members only from a complete, explicitly present-tense roster in a cited Wikipedia revision. The selector supports English summary lists that declare a total and enumerate every member; each name must resolve within the group's membership statements and have accepted evidence in that same list. Incomplete, conflicting, truncated or unsupported lists supply no member-count criterion. Any extra membership statement without explicit former-member evidence blocks the count. Historical membership facts stay available to other games, and a missing end date alone never proves current membership. Explicit periods that contradict the puzzle's reference date veto the count. Former-member proof counts only inside the cited revisions. A positive `current_members` claim for an excluded person blocks the count, as does explicit former-member or departure evidence for a listed person in a revision that also supplies a current roster. A former-member claim from an older, unrelated revision does not by itself veto the current list. A list may end with one clause naming who left, such as `..., while former member Wonho left the group in October 2019.`: the clause adds no member, cannot name anyone on the list, and the person it names still needs former-member proof in the same revision. Among agreeing lists, the newest revision supplies the evidence; selection uses source identity (page, revision, text), never local row ids, so equivalent databases yield equal bytes. Proof is limited to the cited revision; later roster changes require a data refresh. The grid searches only criteria with at least three groups.

The facts stage runs with `--facts`, `--facts-limit`, or `--facts-report`. It records entities, aliases, facts, and evidence. The coverage CSV shows, by group and predicate, how many facts were accepted, rejected, replaced, or left in conflict. Without `--facts-report`, the file `facts-coverage.csv` lands beside the database. Re-running the stage updates each fact by its Wikidata statement ID.

`--releases` uses the WDQS only to discover candidates; the query and its response are kept as snapshots with SHA-256. Each QID is then fetched again through `wbgetentities`, and class, artist, date, and genre are confirmed against that direct snapshot. The pipeline queries the `enwiki`, `ptwiki`, and `kowiki` sitelinks, resolves the title through each wiki's API, and records the revision of that entry. `performed_by` and `released_on` only enter the accepted set when an approved Wikidata reference or that revision's text confirms the relationship. Missing pages, lists, disambiguation pages, pages linked to a different QID, and pages with an extract above the 32 KiB limit are recorded in `release_source_pages`. The default limit is 25 groups per query and 100 candidates per group. Anyone can add a P175 statement that names a group, so a group can come back with more candidates than that. Such a group keeps the 100 distinct candidates with the lowest QIDs, compared as numbers (`Q123` before `Q1000`), whatever the order of the answer, and the run goes on with exit code `0`. New Wikidata items get higher QIDs, so a burst of items created after the discography is what the cut leaves out. Older items have low QIDs, so an editor who adds P175 and P31 to existing old items moves them ahead of the discography and pushes legitimate releases out of the 100. The CLI writes `WARNING: WDQS returned <N> release candidates for group <QID>; kept the 100 with the lowest QIDs and discarded <N - 100>` to stderr, prints the same text as `::warning title=Release candidates truncated::` under GitHub Actions, and adds `Release discovery: <n> group(s) truncated at 100 candidates` to the summary. The warning carries only the group QID, read from the database, and the counts. `release_discovery_groups.candidates_discarded` records the count per run and group, and `release_discovery_groups.last_kept_wikidata_id` records the highest QID the cut kept, only for a truncated group. A release QID must be canonical, `Q[1-9][0-9]*` in ASCII digits, or the discovery fails; group QIDs in the query follow the same rule. In a truncated group, an accepted release stays accepted with its facts and pages only when its QID comes after the last kept candidate and the run has no candidate for it, because it may be one of the discarded candidates. Every other accepted release of the group follows the rule of a complete discovery, so a missing release at or below the last kept QID, or a kept candidate the run rejected, becomes stale. The kept candidates go through the usual confirmation and enter as accepted with new facts. A WDQS response above 5 MB still fails the run with exit code `65`. [ADR 034](docs/decisions/034-descoberta-de-lancamentos-trunca-sem-abortar.md) records the decision.

Since `text-evidence-v6` the rule also recognizes English `It was released by <labels> on <exact date>` after a named release lead. The label list uses capitalized names, at most four labels and 120 characters. The date must match the day-precision P577 value in the same sentence. The antecedent must describe the named release itself with a nominal release type and an optional artist credit. In the artist's name, only the first word may begin with a parenthesis, as in `(G)I-dle`; a later parenthesis is read only as the artist's other name, as in `Day6 (Even of Day)`, so `Foo (Bar) Baz` is not an artist name. The rule covers only artist names that follow a description such as `group` or `band`. The other names of the antecedent have no other name after them, so any of their words may begin with a parenthesis: a sub-unit's parent named without a description, as in `WJSN (Cosmic Girls)`, the three members after `consisting of members`, as in `Sol (Taeyang)`, the studio album a song comes from, as in `Pinocchio (Danger) (2011)`, and the departed member of a bridge, as in `Jae (Park Jae-hyung)`. A descriptive bridge may identify the band's first release since a member's dated departure. Other intervening sentences and ambiguous descriptions are rejected. Planning, territory, format, and reissue scopes are excluded in both the antecedent and the date sentence. A song's explicit origin in a reissued studio album and language adjectives such as Japanese do not scope the song's date or imply a territorial date. A bounded continuation of the date sentence may describe the release's contents, role in a series, or distribution. This syntax does not add `through`, infobox dates, languages, release types, or performer credits. Evidence keeps the original page, revision, and Unicode date span. Existing identity checks, qualified-date rejection, and conflict validation still apply.

Since `text-evidence-v8`, a performer name shorter than four characters, with no space or digit, counts in a credit only when it has at least two characters, a capital letter, and the exact spelling, case included: `Can` never matches `can` or `CAN`. The other conditions of the credit rule still apply, and the rule only confirms the performer that P175 already declares. The title of the group's own catalog page adds a spelling only when it is a known alias in another case, such as `Exo` for `EXO`. A one-letter stage name such as `V` counts only as a whole item, spelled exactly, of an explicit member list (`consists of`, `members:`, `line-up of`) with at least one other item. [ADR-028](docs/decisions/028-evidencia-de-nome-curto.md) records the rule and its limits.

Fact extraction also stores the wikitext of each group revision it reads, as a separate snapshot. When neither a Wikidata reference nor the summary proves a record label or a member, an item of the page's `Infobox musical artist` can: the item must be the value itself, and the evidence points to its characters in that revision's wikitext. [ADR-019](docs/decisions/019-evidencia-da-infobox.md) records the rule and what it leaves out. Comments around a list template, as in `{{hlist|...}} <!-- note -->`, do not hide the list or become items; locators keep the offsets of the original wikitext.

Since `text-evidence-v9`, a `formed_on` with year precision and no reliable Wikidata reference is also accepted when the wikitext of the same revision links `[[Category:Musical groups established in YYYY]]` with the same year, outside comments. The evidence points to that link (`#wikitext[start:end]`). Month or day precision is never proved by the category. When such a category names another year, the fact is rejected as `formation_category_year_differs` at any precision, even if the summary sentence names the Wikidata year, and the link read stays in `fact_issues`. [ADR-029](docs/decisions/029-ano-de-formacao-pela-categoria.md) records the rule, its limits and the known divergences.

For `born_on` and `born_in` with no accepted Wikidata reference, fact extraction also collects the English Wikipedia page of the person (title from the `enwiki` sitelink, fixed revision, wikitext) into `person_source_pages`. Only the `birth_date` and `birth_place` fields of the first infobox (`Infobox person` or `Infobox musical artist`) of that page can prove the fact, and only when `pageprops.wikibase_item` is the person's QID and the title is not a redirect. A date must equal the Wikidata date (the year only, for year precision); a place must be a whole infobox item equal to the place's name or alias. A different value is rejected as `wikipedia_value_differs`, an unreadable one as `wikipedia_value_ambiguous`, and the text read stays in `fact_issues`. The summary, the body, categories and group pages never prove a person attribute. [ADR-027](docs/decisions/027-evidencia-de-pessoa-pela-infobox.md) records the policy change, license, attribution and limits. `text-evidence-v7` is the first rule version that includes this person-page rule. The rule is opt-in: `--facts` and `--releases` alone never enable it, no environment variable or workflow does, and the daily cron neither collects person pages nor accepts a fact from this source. `python main.py --person-evidence` (with `--facts`, `--facts-limit`, `--facts-report` or `--releases`) turns it on and refuses the resolved default `data/kpop.db` and `data/raw` paths. This check does not prove the target is a copy; copy both to a directory on disk and pass `--database <copy>/kpop.db`. A run without the option fetches no person page and accepts no new fact from this source, but keeps the facts the rule had already accepted by replaying the stored revision; if it cannot, it fails with `PersonEvidenceUnavailable` and changes nothing. Every facts run prints the `born_on` and `born_in` coverage before and after. Collecting and reprocessing the production database is a separate, audited step.

The decade criteria of the grid describe the formation year (`formed_on`, Wikidata P571) and are labelled "Formado nos anos …" / "Formed in the …"; a debut date never proves them. Grids published before the wording changed (labels "Estreou nos anos …" / "Debuted in the …") are shown with the new wording by the web app, only when the criterion is `formed_on`, its id names a decade and both labels read exactly as the old pair of that decade; the published file, `grid_id`, criterion ids and saved games do not change. A group enters a criterion only when the cited revision proves that value, so a real group can be missing from a cell for lack of proof, and the game says so after a guess is not accepted: only proven facts count, and the guess is still used. Coverage on a database is measured by regenerating it, not by the published file; the figures for each change belong in its pull request.

`python -m kpop_scraping.quiz_cli` reads the database without running collection. It writes a bilingual dataset and a report as canonical JSON. `--session-output` also writes a ten-question session. The `--session-language`, `--theme`, `--group`, and `--play-mode` filters can be combined. `--timer-seconds` records the limit in the session configuration.

To enable relevance filtering, run the two relevance commands before generating the quiz dataset. `group_relevance_cli` caches 365 completed UTC days of English Wikipedia pageviews for each accepted group linked to an English article. `group_relevance_score_cli` converts one complete collection into catalog percentiles and stores the score, coverage, and algorithm version. Without a complete score run, dataset generation keeps the previous unfiltered behavior. Limited trials cannot affect sessions because the scorer requires one run that covers the full eligible catalog. [ADR-014](docs/decisions/014-pageview-relevance.md) defines the calculation and its source limitations. The separate [group signal report](docs/group-signals.md) is diagnostic and does not enter the score.

`schemas/quiz-dataset-v2.json` and `schemas/quiz-session-v2.json` describe the public contracts. `challenge_rating` records the original factual complexity; `play_mode` selects the assisted, standard, or expert mode. In assisted mode a person option carries a `(groups)` suffix only when the prompt names no entity. On member questions the suffix would repeat the asked group on the answer option, so generation rejects any option label that echoes the entity named in the prompt. Age and birth date prompts, in every mode, name the person with the same `(groups)` suffix, because stage names repeat across groups (Hyunjin of Stray Kids and of LOONA); their options are numbers or dates, so the suffix gives nothing away. The suffix states a membership, so these questions cite it: after the birth fact, `fact_base_ids` and `evidence` list the `has_member` and `member_of` facts of each named group, in the suffix order. The `semantic_id` and the decade clue still come from the birth fact alone. Decade clues point to accepted facts and their evidence. A clue is either the question's own dated fact (year of formation, release or birth) or, on questions whose answer is a group, a release or a person and that show no dates, the answer's own accepted formation, release or birth date, cited with its own revision and location; for that reason a clue's `fact_base_ids` need not be among the question's, but every fact it names must have evidence. A client released before this rule rejects the whole session that carries such a clue, and it reads `manifest-v2.json` on every game it starts. So `manifest-v2.json` only lists sessions every released client accepts (publication refuses and `--verify` fails on a clue outside its question's facts), and the sessions with the answer-date clues are listed in `manifest-v3.json`, which has the same shape and the same session ids, question ids and options, differs only by clues, and is published only with `daily_puzzles_cli --related-clues` (the cron passes it when the repository variable `QUIZ_RELATED_CLUES` is `true`). The current client reads `manifest-v3.json` first and falls back to `manifest-v2.json` when it is absent or unusable; an older client never requests it, so no waiting for old tabs to disappear is involved, and removing the variable returns every client to `manifest-v2.json`. Without the flag the output is the one published before the manifest existed, and the report counts the questions as `related_clues_not_enabled`. A clue is published only when it rules out at least one option and leaves at least two; an option with no dated accepted fact is never ruled out, and a question with no safe clue has `clues_available: []`. The game then says so in one line ("Sem pista nesta pergunta." / "No clue for this question."), in Assisted and Standard, without a button and without a point cost, and keeps that line after the answer so the options under it do not move; Expert has no clues by design and says nothing. After answering, the source panel lists the sources of the clues the player saw. The generation report (`kpop-quiz-generation-report-v4`) counts `clue_coverage` by question type and the reasons a question has no clue, and `web_publish` and `daily_puzzles_cli` print how many published questions and sessions carry a clue, by mode. The same input, version, mode, and seed produce identical bytes. The v1 contracts stay versioned for older consumers.

The static question catalog ([ADR 026](docs/decisions/026-catalogo-estatico-de-perguntas.md)) feeds new general-quiz selections. `catalog-manifest-v1.json` (`kpop-quiz-catalog-manifest-v1`) names six shards, one per language and play mode (`catalog.<locale>.<mode>.<sha256>.json`, `kpop-quiz-catalog-v1`). Each shard carries every eligible question with its evidence and lists, in `pools`, the indexes allowed for the unfiltered game and for each decade. Publisher, `--verify` (and `--require-catalog`), and the web consumer (`web/src/data/catalog-loader.ts`) all check integrity, schema, identity, language, mode, version and eligibility before exposing questions. An invalid or corrupt catalog is a closed error with no fallback to unvalidated content. When the catalog is absent, the general Quiz falls back to the published legacy sessions (operator decision 28/10/2026), and its result says, beside "Jogar novamente" / "Play again", that the button repeats the round's questions ("Jogar novamente repete as perguntas desta rodada." / "Play again repeats this round's questions."). The setup has no such button and says nothing about replaying. The general Quiz (`web/src/data/catalog-session.ts`) draws ten distinct `semantic_id`s from the validated catalog, shuffles options like `create_session`, avoids the immediately previous semantic set when another combination exists, says on the result, when only ten questions are eligible, that "Play again" repeats them, and reports unavailability below ten without duplicates or mixed filters. Daily mode keeps the published day session. Catalog-built rounds carry `catalog_version` additively. The Quiz also resumes a local round from `localStorage` (schema `kpop-quiz-progress-v1`) in **one slot per config** (`locale|playMode|theme|decades` → `kpop-quiz-progress:<fnv1a64>`). Visiting another config leaves foreign slots untouched; Start/continue overwrite only the current config’s slot. A legacy single-slot payload at `kpop-quiz-progress` migrates into the matching config slot when compatible and is removed; when it belongs to another config the UI warns and keeps that legacy key and every other slot. Each save restores identity, sequence, pending selection, history, clues, the absolute timer deadline and completion, validates against the current artifact before restoring, never treats an open give-up confirmation as authorized after reload, and does not duplicate stats when a finished round is reopened (results stay on screen, with Play again in the general Quiz). Analytics consent does not gate this persistence. Browser `localStorage` is typically ~5 MiB per origin; each slot embeds a full session, and a failed `setItem` surfaces the explicit unavailable notice without clearing other slots. Publish with `daily_puzzles_cli --catalog` or `web_publish --catalog` (the cron passes `--catalog` when the repository variable `QUIZ_CATALOG` is `true`). Without the flag a catalog left by an earlier run is withdrawn and session manifests keep their previous bytes. The catalog lives in the main data directory only, never under `next/`, and follows the database of the run rather than a kept day. This change does not turn `QUIZ_CATALOG` on.

`schemas/timeline-puzzle-v2.json` describes `timeline.daily.json`. v2 adds the `release` event type to v1; the generator writes v2, and the Python and web validators still accept v1, because a day already published keeps its bytes. The date seed picks one of four themes: group formations, K-pop generations, idol births, and releases (pt-BR "Lançamentos"). A release event comes from one accepted `released_on` fact; its title names the artist only when an accepted `performed_by` fact exists, and the evidence of both facts goes with the event. Releases with more than one accepted date, or whose title and artists repeat another release, stay out. When a theme's pool cannot fill 5 events, the generator tries the next theme, so a database without release facts still publishes a timeline. [ADR 012](docs/decisions/012-mecanica-linha-do-tempo.md) has the selection rules.

The collector applies pending migrations when it opens the database. Each migration runs inside a transaction. Databases created by an earlier version keep their runs and pages through the migration.

## Daily publication workflow

The `date` input of `daily-puzzles-cron` accepts a real calendar date as `YYYY-MM-DD`, or stays empty to use the current date. The value reaches the job as an environment variable and is passed to the generator as a separate argument. The step fails before generating puzzles if the date is malformed or does not exist.

Publishing refuses a date older than the day already installed, including with `--regenerate`. Use a separate output directory for historical exports; `--dry-run` can inspect an older date without changing published files. Rotation preserves both grid and crossword publication records when replacing `next/`, including when the scheduler skips a day. Replacing a crossword record archives its previous contents under `crossword-history.<date>.<hash>.json`; re-running identical records does not duplicate that history.

The publication job also checks that the live data tree still matches the revision used for generation. If another change replaced data while generation ran, publication fails before copying files; rerun the full workflow to generate from the new revision. Local installation copies a complete directory snapshot before swapping it into place. If the process stops between directory renames, the next publication read restores the previous directory from its sibling backup; the destination is not left with a partially copied set. A brief absence is possible between those renames, so the local output directory is not a live-serving boundary. Run one publisher per output directory. Only verified data is committed for deployment.

`daily-puzzles-cron` and `map-pilot-refresh` push the generated commit to an automation branch (`automation/daily-puzzles`, `automation/map-pilot-refresh`) and merge it through a pull request with `scripts/publish_via_pr.py`. The self-merge only accepts the commit the job itself pushed: the script merges a pull request whose head branch is in this repository and whose head is that commit, and opens the pull request when the repository has none. A pull request from a fork is never merged, whatever its branch name or its position in the listing. The merge passes `--match-head-commit` with the pushed SHA, so a push that reaches the branch after the check fails the step and that run publishes nothing. [ADR 031](docs/decisions/031-self-merge-so-do-commit-enviado.md) records the rule.

### Partial publication

Each game of the day is generated and validated on its own, and any exception, `MemoryError` included, leaves only that game out ([ADR 037](docs/decisions/037-publicacao-parcial-do-dia.md)). `KeyboardInterrupt` and `SystemExit` still stop the run, because they are the run being cancelled. The day goes out with the other games, and the omitted game's file is removed from the directory so an earlier day's copy cannot stand in for it. The set of day D is generated at noon on D-1, under `next/`. When it leaves a game out, the page of that game shows the D-1 board marked as an earlier day's from midnight to noon of D. From noon of D, when the cron promotes the set, to noon of D+1, about 24 hours, the page shows its `missing` state, even when `next/` already holds that game's next board. Of the five games this policy added, only the timeline loader reads `next/` when the main directory has no file; the other four read `next/` only from a file in the main directory, as the group code does. The grid and crossword loaders read `next/` even without the main file. The build, the web and Python tests and the end-to-end smoke test accept the absence too (see below). The runner result records each omission, and the CLI prints one `::warning` per game in the run summary:

| Game | Published file | Result field | Warning title |
| --- | --- | --- | --- |
| Quiz (both languages) | `manifest-v2.json` and its sessions, `manifest-v3.json`, `session.pt-BR.json`, `session.en.json` | `quiz_skipped` | `Daily quiz missing` |
| Grid | `grid.daily.json` | `grid_skipped` (`grid_reused` when the previous grid stands in) | `Daily grid missing` |
| Connections | `connections.daily.json` | `connections_skipped` | `Daily connections missing` |
| Name guess | `name-guess.daily.json` | `name_guess_skipped` | `Daily name guess missing` |
| Word search | `word-search.daily.json` | `word_search_skipped` | `Daily word search missing` |
| Timeline | `timeline.daily.json` | `timeline_skipped` | `Daily timeline missing` |
| Group code | `code-groups.daily.json` | `code_groups_skipped` | `Daily group code missing` |
| Crossword | `crossword.daily.json` | `crossword_skipped` | `Daily crossword omitted` |

For the quiz, connections, name guess, word search and timeline, a generated day reports `{"error": "<reason>"}` and a kept or promoted day reports `{"error": <recorded reason or null>, "published_without": true}`. The grid, group code and crossword fields keep the shapes described above. The reason is one line of at most 500 characters: the message of a `ValueError`, or the exception type and message of any other error. Control characters become spaces, and the warning escapes `%`, CR and LF, so text quoted from Wikipedia or Wikidata cannot start a workflow command of its own. That full reason goes to the log, the warning and the runner result only.

Every set the runner generates carries `daily-set.json` (`kpop-daily-set-v1`): the set's date and, under `omitted`, the reason for each game without a file. The record is public, so its reason is a short category, `generation failed (<exception type>)`, and never an exception message, which may hold a local path. That holds for the crossword too; its own publication record (`crossword-publication.<date>.json`), also public, keeps the message of a `ValueError` or `sqlite3.Error` as it did before, and only the type of any other error. The runner and the board swap gate date a set by this record, so a set without `connections.daily.json` is still recognized as the day already served, kept instead of generated again, and its other boards are still compared by the gate. Verification refuses a set whose record lists a game that still has a file, a required file missing without a listing, a board other than the grid whose `reference_date` differs from the record, or a daily quiz session (and `session.<locale>.json`) whose seed `kpop-daily-<date>` names another date. A set published before the record is dated by `connections.daily.json` and keeps the earlier rules. An unreadable record in the main directory stops the run before it writes anything; in `next/`, which every run builds again, it counts as no set.

A failure in the next day's set never undoes the day already installed. When some games of D+1 fail, `next/` holds the partial set. Any other exception while generating or publishing D+1, including every game failing, leaves the reference day installed, reports `next_skipped` and prints the warning `Next day not published ahead`. A failure before the atomic install leaves `next/` as it was, and a `next/` that fails verification after it is removed. The next run builds it again, and in the cron the main directory already holds the day being served. A `workflow_dispatch` with a past `--date`, run after midnight in Sao Paulo, is the exception: its `next/` is the day the site serves, and removing it sends the site back to the earlier board until the next run. When the promoted set lacks a game, the main directory loses the previous day's file for it.

`python -m kpop_scraping.daily_puzzles_cli` exits 0 for a complete or partial day. It exits 1 only when no game of the reference day could be generated (`NoGamePublishedError`, raised before any file is written) or when the published set fails verification. A grid kept from the previous day and an omitted crossword do not count as generated games. When the question catalog is on and cannot be built, the run withdraws it and reports `catalog_skipped`.

`Generate daily puzzles` has `timeout-minutes: 20`. A normal run takes under a minute, and with `cancel-in-progress: false` a stuck run would hold the concurrency group and delay the following ones.

The tests and the deploy checks accept a day without any of these games. The tests that used the published files as input read frozen copies (`tests/fixtures/web_publish/`, `web/src/tests/fixtures/`). The checks of the published files validate each game's file when it is there and skip a game the day left out. The end-to-end smoke test asks the site whether each file is published. With the file, the page must show the board. Without it, the page must show the missing state (`data-testid="game-missing"`, `data-error-kind="missing"`), and an `invalid` state always fails. The timeline may show the board from `next/` and the quiz may build a general round from the question catalog.

To revert the partial publication, delete `web/public/data/daily-set.json` and `web/public/data/next/daily-set.json` as well. The earlier code installs the main directory without removing files it does not know, and a stale record would keep naming a day already past; if this code came back, verification would refuse the set ("is for X, but daily-set.json publishes D") until the next cron run.

### Database rebuild and fallback

The job refreshes `data/kpop.db` in two steps, in this order. [ADR 032](docs/decisions/032-rebuild-com-fallback-em-passo-separado.md) records the decision.

1. `Rebuild database from Wikipedia and Wikidata` runs `exec python3 scripts/rebuild_database.py rebuild --database data/kpop.db -- python main.py --facts --releases --database data/kpop.db`. The script copies the cached database to `data/kpop.db.cached` and runs the collector at most 3 times, 10 minutes apart. Each attempt has 30 minutes. Past that, the script sends SIGTERM and, 30 seconds later, SIGKILL. The step has `continue-on-error: true` and `timeout-minutes: 120`. Its worst case is three attempts of 30.5 minutes plus two waits, 111.5 minutes. When the step times out or the run is cancelled, the runner sends SIGINT, SIGTERM and SIGKILL to the PID of the step's shell and to no other process. `exec` replaces the shell with the script, so the signal reaches it; the script kills the running attempt and exits with `130` (SIGINT) or `143` (SIGTERM). Without `exec`, the SIGTERM would end the shell and leave the script and the collector writing while step 2 replaces the database.
2. `Restore cached database` runs only when step 1 failed or hit its timeout (`if: steps.rebuild.outcome == 'failure'`). `python3 scripts/rebuild_database.py restore-cache --database data/kpop.db` deletes the raw snapshots the attempts wrote, deletes the SQLite `-journal`, `-wal` and `-shm` files a stopped attempt leaves beside the database, puts the cached copy back and emits the `Database not refreshed` warning with the reason. Without a cached copy the step fails and the run publishes nothing.

`Generate daily puzzles` and the steps after it run after either path, because a failed rebuild step does not fail the job.

The script reads the exit code of each attempt to decide whether to run another. `kpop_scraping/exit_codes.py` names the codes of `python main.py`:

| Exit code | Meaning | What the rebuild does |
|---|---|---|
| `0` (`EXIT_OK`) | The database was refreshed, including a run that cut a group at the WDQS candidate limit or kept the stored snapshot of a page whose extract changed without a new revision | Ends; the restore step is skipped |
| `75` (`EXIT_TRANSIENT`) | A client gave up on a condition that passes with time: network failure, `maxlag` past the run's wait budget, HTTP 429 or 5xx, a `Retry-After` above the client's limit | Waits 10 minutes and runs again, up to 3 attempts |
| `65` (`EXIT_DETERMINISTIC`) | Any other handled failure: `SnapshotIntegrityError` (for example a damaged snapshot file), a validation `ValueError`, a response the parser refuses, a WDQS response above 5 MB | One attempt, then the cached database |
| `1` or any other code | Uncaught exception, or an argument refused before the run | One attempt, then the cached database |
| none (attempt timeout) | The script stopped the attempt and exits with `124` | One attempt, then the cached database |

A client marks an error as transient where it gives up, with `MediaWikiError(..., transient=True)`, and the CLI turns that mark into exit code `75`. The MediaWiki client (Wikipedia and Wikidata) and the WDQS client treat `URLError`, `TimeoutError`, `ConnectionError`, `http.client.HTTPException` and `ssl.SSLError` as network failures. The two failure codes are `EX_DATAERR` and `EX_TEMPFAIL` from `sysexits.h`. They differ from `1` (Python's generic error), `2` (argparse) and `124`, `137` and `143` (timeout and signals).

Environment variables replace the limits, and the tests use them to run in seconds: `REBUILD_MAX_ATTEMPTS` (3), `REBUILD_ATTEMPT_TIMEOUT_SECONDS` (1800), `REBUILD_RETRY_WAIT_SECONDS` (600) and `REBUILD_KILL_GRACE_SECONDS` (30). The workflow sets none of them. `tests/test_rebuild_database.py` fails when the worst case of the defaults no longer fits in the step's `timeout-minutes`.

The app stays static: answers and the next day's set, published ahead of time to tolerate scheduler delays, can be read from the public files. Hiding them until game time would require serving the daily set from a backend with a different availability policy.

#### Waiting for `maxlag`

Every request to the Action API of Wikipedia and Wikidata sends `maxlag=5`. While the replicas, or Wikidata's query service, lag more than 5 seconds, the API answers with the `maxlag` error instead of data. In November 2026 Wikidata's lag stayed between 9 and 14 seconds for hours on most nights. The collector then gave up after 3 retries, 5 seconds apart (the `Retry-After` MediaWiki sends), so the 3 attempts of a night failed within about 20 minutes and the day was published from the cached database.

The collector waits the lag out. After a `maxlag` answer the client sleeps for the longer of the answer's `Retry-After` and the `lag` it reports (5 seconds when it gives neither), at least 5 and at most 120 seconds, and sends the same request again. MediaWiki sends `Retry-After: 5` for `maxlag=5`, so in practice the reported `lag` sets the pause. These pauses come from one budget per run of `python main.py`, shared by every Wikipedia and Wikidata client of the run: 15 minutes by default, or `MAXLAG_BUDGET_SECONDS`. When the budget runs out, the client raises `MediaWikiError(..., transient=True)` with the message `MediaWiki maxlag at <API> did not clear within the run's <N>s wait budget (MAXLAG_BUDGET_SECONDS); last answer: <server message>`, and the run exits with `75`. The backoff for network and HTTP errors keeps its own 3 retries and draws nothing from the budget. The WDQS client (`release_discovery.py`) needs no budget: the SPARQL endpoint takes no `maxlag` parameter and never answers with that error; its overload reaches the client as HTTP 429 or 5xx.

The budget fits the attempt and the night:

- One attempt gives up on `maxlag` after 15 minutes of pauses plus the work, which takes about 2 minutes. That is half of the 30-minute attempt timeout, so a persistent lag ends in `75` and gets another attempt. An attempt stopped by its timeout exits `124` and is not repeated. `tests/test_rebuild_database.py` fails when the default budget exceeds half the attempt timeout.
- With 3 attempts and 2 waits of 10 minutes, the rebuild falls back to the cache only when the lag lasts for about 70 minutes, against about 20 before.
- The schedule asks for 15:00 UTC and GitHub has been starting the job between 19:00 and 24:00 UTC. Midnight in Sao Paulo is 03:00 UTC. A run that starts at 24:00 UTC and spends the whole budget on all 3 attempts finishes the rebuild at about 01:15 UTC. Even the step's 111.5-minute worst case ends at about 02:00 UTC, an hour before midnight in Sao Paulo, with time left for generation and publication.

The workflow does not set `MAXLAG_BUDGET_SECONDS`, and a test fails if it does. `python -m kpop_scraping.map_pilot_refresh` builds its Wikidata client with a 5-minute budget, because its workflow runs it up to 4 times, 15 minutes apart, inside a 90-minute step. [ADR 033](docs/decisions/033-espera-por-maxlag-e-versao-das-regras.md) records the decision.

#### Evidence rules version

Each fact run records the `EVIDENCE_RULES_VERSION` (`kpop_scraping/evidence.py`) that decided its facts in `fact_runs.evidence_rules_version` (migration 11); the fact stage and the release stage both fill it, and runs from before the migration keep `NULL`. `run_daily_puzzles` returns `evidence_rules`, with the version of the code (`code`) and the version of the last completed fact run in the database (`database`, `None` when the database never recorded one). `daily_puzzles_cli` prints `Evidence rules: database <version>, code <version>`; when the two differ, it writes a warning to stderr and, in GitHub Actions, emits `::warning title=Evidence rules differ::` with both versions. That happens when the run restored a cached database collected before a change of the evidence rules: the day is published with facts decided by the older rules, and the run summary says so. The value lives only in the result of the run and in its log; no published file carries it, and `web/` reads nothing new.

## Pinned GitHub Actions

Every Action in the five workflows (`daily-puzzles-cron`, `pages`, `staging`, `e2e-nightly`, `map-pilot-refresh`) is pinned to a full commit SHA, with the exact release tag in a trailing comment (for example `# v7.0.1`). To update one, check out the new release tag, copy the SHA it resolves to (`git ls-remote --tags https://github.com/<owner>/<repo>`) and replace both the SHA and the comment in every workflow that uses it. `.github/dependabot.yml` opens weekly pull requests for these pins.

## Gate factual do Venn

`python -m kpop_scraping.venn_cli --database data/kpop.db --date 2026-10-12 --output /tmp/venn-report.json --sample-output /tmp/venn-sample.json` mede cobertura sem rede, coleta ou escrita no SQLite, aberto em modo somente leitura. O contrato v1 aceita apenas pessoas com nascimento aceito, data gregoriana completa, precisão de dia, revisão e local de evidência, sem conflito aberto ou datas inconsistentes. Ausência de data/evidência significa `unknown`, nunca `false`. As três categorias são nascimento antes de um ano observado, janeiro–junho e dias 1–15; os bits são respectivamente 1, 2 e 4. Datas completas sustentam também exclusões. Não são usados gravadora ausente ou número incompleto de integrantes.

O relatório contém candidatos, rejeições, classificações `true`/`false`/`null`, contagens das oito regiões e, quando possível, sete QIDs distintos cobrindo masks 1–7. A busca é finita e determinística. Os contratos estão em `schemas/venn-coverage-report-v1.json` e `schemas/venn-coverage-sample-v1.json`. Código de saída **0** indica gate aprovado, **2** indica `insufficient_coverage` e **1** indica entrada inválida ou falha de verificação. Cobertura insuficiente remove uma amostra anterior no caminho solicitado e mantém o jogo dependente suspenso.

`python -m kpop_scraping.venn_cli --database data/kpop.db --verify /tmp/venn-report.json --verify-sample /tmp/venn-sample.json --output /tmp/venn-verified.json` recompõe o relatório e verifica todos os dados, masks, evidências e identidade da amostra contra o banco declarado e a data do relatório. As saídas são substituídas atomicamente por arquivo. Esta etapa comprova elegibilidade apenas, sem jogo ou cadência diária.

## Cruzadinha

A cruzadinha fica em `/pt-br/cruzadinha/` e `/en/crossword/`, no menu de
jogos, no sitemap e com cartões OG. Uma grade nova de 3 a 5 grupos sai por
dia, gerada pelo runner diário (`crossword.daily.json`, contrato
`crossword-daily-v1`), sem repetir grupos da véspera. Use as pistas para escolher a
palavra, digite por célula (Tab e setas), verifique a grade quantas vezes
quiser ou revele as respostas. O resultado mostra o veredito, o
compartilhamento e o painel "Ver fonte" com os trechos e as revisões citadas.

Backspace apaga a casa preenchida. Numa casa vazia, volta à anterior da
palavra selecionada e apaga sua letra; na primeira casa vazia não faz nada.
A direção selecionada permanece nos cruzamentos. Tocar ou clicar de novo na
casa que já tem o foco, num cruzamento, troca a palavra entre horizontal e
vertical. Tab passa à casa seguinte, linha por linha, e as setas levam à
próxima casa na direção da seta. Ao focar ou digitar, a página rola quando
necessário para manter a casa acima da barra e do banner de consentimento.
Escolher uma pista na lista, que no celular fica abaixo da grade, traz de
volta à tela a pista ativa e a grade inteira quando as duas cabem acima da
barra.

Uma verificação sem vitória marca as casas erradas ou vazias com fundo,
triângulo no canto e `aria-invalid="true"`. A barra diz quantas são ("3
quadrados a corrigir."), e o foco volta à casa em que o jogador estava, com a
mesma pista. Numa partida restaurada, antes de tocar na grade, o foco fica no
botão. Editar uma casa tira a marca dela; a próxima verificação refaz as
marcas. A frase cabe numa linha, então a barra fixa não cresce.

As rotas antigas `/pt-br/cruzadinha-piloto/` e `/en/crossword-pilot/`
respondem `301` no Cloudflare Pages pelo `web/public/_redirects`; no GitHub
Pages de homologação elas dão 404, como no código de grupos
([ADR 023](docs/decisions/023-promocao-de-piloto-a-jogo.md)).

O input transforma letras em maiúsculas, remove acentos, espaços e pontuação,
e conserva dígitos. Apenas a grafia canônica normalizada ocupa a grade. Aliases
são verificados para colisões entre as identidades selecionadas. As pistas
usam fatos `accepted` e evidência de revisão Wikipedia. A seleção confronta
cada conjunção de fatos com todos os grupos do SQLite, e rejeita uma pista
que corresponda a mais de uma identidade. A ausência de fatos em outros
grupos limita essa prova ao snapshot coletado, não a todo o universo K-pop.

```bash
python -m kpop_scraping.crossword_cli --database data/kpop.db --output web/public/data/crossword-pilot.json --reference-date 2026-10-12
python -m kpop_scraping.crossword_cli --verify web/public/data/crossword-pilot.json
```

A CLI abre o SQLite em modo read-only e seleciona apenas o tabuleiro auditado
BTS / BtoB / SISTAR, que o site serviu até a integração diária. O arquivo
continua publicado: antes do primeiro registro diário, o runner lê esse
tabuleiro como a partida da véspera. O contrato `crossword-pilot-v1`
(`schemas/crossword-pilot-v1.json`) declara modo, identidade do piloto,
impressão SHA-256 do conteúdo selecionado, data de referência, dimensões,
entradas, aliases, coordenadas, pistas PT/EN, evidências e células, sem campos
extras. O schema cobre a estrutura; `validate()` em
`kpop_scraping/crossword_cli.py` e `validateCrosswordPuzzle()` em
`web/src/data/crossword.ts` rejeitam os mesmos casos, lidos de uma fixture compartilhada
(`tests/fixtures/crossword_invalid_cases.json`, rodada pelos testes Python e
Vitest). A verificação recalcula a impressão em JSON
canônico compacto e testa as invariantes sem consultar o banco. A impressão
detecta alterações, sem garantir a autenticidade editorial da fonte.
`matching_qids` registra o conjunto observado pela seleção, e
`audited_group_count` informa o tamanho do vocabulário comparado. A seleção
exclui conflitos abertos e candidatos sem evidência. A saída é atômica e não
pode apontar para o banco de origem. O validador rejeita cruzamentos
incompatíveis, grade desconectada, células órfãs, colisões de aliases, pistas
sem fonte e revisões inconsistentes.

A página só joga a grade datada de hoje (horário de São Paulo), lida de
`data/` ou, publicada antes, de `data/next/`. Uma grade de outro dia nunca
aparece no lugar da de hoje: sem envelope nem registro do dia, a página diz
que a cruzadinha ainda não foi publicada; com o envelope omitido, diz que não
há cruzadinha hoje; com só o registro `omitted` (histórico da véspera ausente
ou erro de geração), diz que a cruzadinha de hoje está indisponível, sem
mostrar o motivo interno. O navegador confere o checksum do envelope, o
histórico, a contagem de tentativas, a geometria, as fontes e a exclusão da
véspera; a correspondência factual e a prova de unicidade são recalculadas
pelo runner, que tem a base. O progresso fica no
`localStorage` em `kpop-crossword-<dataset_version>` (checksum do envelope,
que cobre a data), a partida concluída conta uma vez nas estatísticas (aba
"Cruzadinha" / "Crossword", no dia local em que terminou) e o texto
compartilhado traz a data, o veredito e um quadrado por palavra, com
`utm_campaign=crossword`. Resolver com "Verificar
respostas" conta como vitória; "Revelar respostas" conta como partida sem
vitória. Detalhes em [Cruzadinha](docs/crossword-game.md).

Os arquivos publicados incluem respostas, como os demais jogos estáticos.
Falhas de conteúdo aparecem com opção de tentar novamente, sem fixture de
substituição. As fontes Wikipedia mantêm atribuição e CC BY-SA 4.0; o cadastro
Wikidata usa CC0. Nenhuma fonte externa foi acrescentada.

## Jogo de código de grupos

O jogo de lógica fica em `/pt-br/codigo/` e `/en/code/`, no menu de jogos, no sitemap e com cartões OG. Seis grupos distintos do catálogo aceito servem como símbolos. O jogador descobre uma sequência de quatro sem repetição em dez tentativas, com contagens agregadas de posições exatas e grupos deslocados. Um palpite já enviado é recusado sem gastar tentativa, e ao fim da partida o formulário fica desabilitado e o resultado aparece antes do histórico. A sequência sorteada não afirma uma relação factual entre grupos. O artefato diário (`code-groups.daily.json`) segue o contrato `code-groups-pilot-v1` e traz revisões Wikidata da classificação P31.

As rotas antigas `/pt-br/codigo-piloto/` e `/en/code-pilot/` respondem `301` no Cloudflare Pages pelo `web/public/_redirects`; no GitHub Pages de homologação elas dão 404, o que é aceitável porque a homologação inteira é `noindex` ([ADR 023](docs/decisions/023-promocao-de-piloto-a-jogo.md)).

```bash
python -m kpop_scraping.code_groups_cli --database data/kpop.db --date 2026-10-12 --seed group-code-pilot --output web/public/data/code-groups.pilot.json
python -m kpop_scraping.code_groups_cli --verify web/public/data/code-groups.pilot.json
# Conferir também a origem no catálogo do banco
python -m kpop_scraping.code_groups_cli --verify web/public/data/code-groups.pilot.json --database data/kpop.db
```

A geração abre o SQLite somente para leitura e exige seis QIDs aceitos com classificação musical compatível. O mesmo catálogo, data e seed produzem o mesmo artefato. A verificação confere o hash de identidade e rejeita contratos inválidos; carga ausente ou inválida no navegador oferece nova tentativa de carregamento. As fontes de classificação aparecem no resultado. O runner diário publica também o artefato do dia (`code-groups.daily.json`, seed `kpop-code-groups-daily-{data}`); quando a geração falha, o dia sai sem o arquivo e sem bloquear os outros jogos, com o registro em `code_groups_skipped`, e a página avisa que o código do dia não foi publicado. O progresso da partida fica no `localStorage` (`kpop-code-<data>`, com o `puzzle_id` do tabuleiro, e um save de outro tabuleiro da mesma data é descartado), as estatísticas entram na janela de estatísticas e o resultado compartilhado leva ao jogo com `utm_campaign=code`. Detalhes em [Jogo de código de grupos](docs/code-groups-game.md).

## Contrato do Strands

O contrato `kpop-strands-puzzle-v1` fica em `schemas/strands-puzzle-v1.json`, com o validador em `kpop_scraping/strands_schema.py`. O Strands tem gerador e ainda não tem página. O jogador procura palavras ligadas a um tema central bilíngue, o campo `theme` em pt-BR e en, numa grade de letras de A a Z. Os temas iniciais previstos são elencos de grupos e décadas.

A grade tem de 9 a 10 linhas e de 9 a 10 colunas, contadas de forma independente; 9×10 e 10×9 também são aceitos. Cada item de `words` traz `cells`, a trilha em ordem de leitura como pares `[linha, coluna]` a partir de zero, com uma célula por letra. O validador exige:

- passos entre os 8 vizinhos de uma célula, sem repetir célula na mesma palavra nem entre palavras;
- cobertura total: cada célula da grade pertence a exatamente uma palavra;
- nenhum passo diagonal cruza outro em X dentro do mesmo quadrado 2×2, na mesma palavra ou entre palavras;
- letras da grade ao longo de `cells` iguais a `word`;
- de 6 a 9 palavras, contando o spangram;
- exatamente uma palavra com `is_spangram: true`, cuja trilha toca a primeira e a última linha ou a primeira e a última coluna;
- `puzzle_id` igual ao SHA-256 do JSON canônico sem o próprio `puzzle_id`.

A regra do cruzamento em X mantém as trilhas legíveis quando a interface as desenha. Relaxar a regra depois não invalida artefatos publicados.

Palavras do tema exigem `id` (QID), `canonical_name` e `evidence` com revisão e URL https. As duas legendas de `labels` precisam normalizar para `word`.

O spangram declara `spangram_kind`, campo que só ele tem. Com `entity`, o spangram nomeia uma entidade, como o grupo de um tema de elenco. Ele leva então `id`, `canonical_name` e `evidence`, e as duas legendas normalizam para `word`. Com `theme`, o spangram é uma expressão do tema sem afirmação própria, como num tema de década. Os três campos de entidade ficam ausentes e basta uma legenda normalizar para `word`, porque a grade usa uma grafia só para os dois idiomas. As afirmações publicáveis ficam nas palavras do tema.

A unicidade da solução cabe ao gerador; o validador confere apenas a estrutura. O fixture fictício `tests/fixtures/strands_puzzle_valid.json` mostra uma grade 9×9 com seis integrantes e o grupo como spangram `entity`.

### Gerador do Strands

```bash
python -m kpop_scraping.strands_cli --database data/kpop.db --date 2026-11-01 --verify --output /tmp/strands.json
# Palavras, descartes com motivo e tamanhos de grade que cada tema consegue cobrir
python -m kpop_scraping.strands_cli --database data/kpop.db --list-themes
# Benchmark de fechamento e tempo por tamanho de grade
python -m kpop_scraping.strands_benchmark --database data/kpop.db
```

O gerador abre o SQLite somente para leitura e monta uma grade 9×9 por padrão (`--rows` e `--cols` aceitam 9 ou 10). A seed padrão é `kpop-strands-daily-<data>`; a mesma base, seed, data e dimensões produzem o mesmo arquivo, porque o esforço de busca é limitado por contagem de nós. Os temas são elencos de integrantes atuais e antigos documentados por evidência de integração, com o nome do grupo como spangram `entity`, e as décadas de formação 1990, 2000 e 2010, com spangram `theme` em grafia pt-BR. Um tema só entra quando as letras de 5 a 8 palavras mais o spangram somam a área exata da grade e o spangram tem letras para ligar dois lados opostos. Nomes com menos de 3 letras ou com letras fora do alfabeto latino são descartados com motivo.

Antes de publicar, `enumerate_strands_solutions` acha todas as trilhas de cada palavra do tema, com poda por prefixo, e a grade só sai quando existe uma única escolha de trilhas disjuntas para essas palavras. A enumeração tem orçamento determinístico de 100000 nós, compartilhado entre prefixos e combinações de trilhas. Exceder esse orçamento interrompe a geração com `StrandsGenerationError`, sem prova de unicidade. O prazo é verificado durante as buscas e antes da saída; leituras SQLite são verificadas antes e depois da chamada. Palavras fora do tema não entram na prova. `--verify` refaz a prova a partir do JSON. Sem tema viável, sem grade única dentro do orçamento ou ao passar de `--time-limit` (30 s), a CLI sai com código 1 e `StrandsGenerationError`. Na base da medição registrada, só a década de 2010 e o elenco de Girls' Generation cobrem uma grade 9×9. O embaralhamento por seed permite repetir temas em dias consecutivos; números e limites em [Benchmark do gerador Strands](docs/strands-benchmark.md).

### Game measurement with GA4

When production has `PUBLIC_GA4_ID` configured and the visitor accepts analytics,
quiz, grid, connections, name-guess, word-search, timeline, map and code emit
these events:

- `game_start` records the first game action in a round. This is Start in Quiz,
  a tile selection in Connections, a valid letter in Guess, a selection of at
  least two cells in Word Search, reordering or submitting Timeline, an answer
  in Map, an attempt in Grid, or a position choice in Code. Giving up also
  starts an untouched round.
- `game_complete` records finishing or giving up after an interaction in the
  current visit, once per round. Opening a saved result emits neither start nor
  completion.
- `share` records successful native sharing or clipboard copy. Cancellation,
  failure and manual text selection do not count. `method` is `native` or
  `clipboard`, `content_type` is `game_result`, and `item_id` is the fixed game key.
  See [Google's share event contract](https://developers.google.com/analytics/devguides/collection/ga4/reference/events#share).

All events include `game` with one of the eight keys above and `locale` with
`pt-BR` or `en`. Quiz also includes `mode`, either `assisted`, `standard` or
`expert`. Events contain no answers, artist names, shared text, user IDs or
puzzle IDs.

`game_start` and `game_complete` also include `daily`: `yes` for the day's
challenge, `no` for the general Quiz and for a replay of a board already
finished. `game_complete` also includes:

- `outcome`: `win`, `loss` or `give_up`. A give-up counts as `give_up` even with
  a winning score. Word Search and Crossword have no loss and Code has no
  give-up. The other games use the win rule of their stats; Map counts a round
  with at least half the dates right as a win, the same rule as its stats.
- `days_since_last`: `first`, `0` (another round the same day), `1`, `2-7` or
  `8+`. It compares the game's last recorded date, read before this round is
  saved, with the current day in Sao Paulo. A stored date ahead of that day
  sends no value.
- `streak_bucket`: `0` (no active streak), `1`, `2-3`, `4-7` or `8+`, from the
  game's streak after this round is saved.

Both bands are computed in the browser from `player-stats`. Map sends neither,
although it records its stats. A change to the streak or last-date rules in `player-stats`
changes what the bands mean from that release on.

Register `game`, `locale`, `mode`, `daily`, `outcome`, `days_since_last` and
`streak_bucket` as event-scoped dimensions in GA4 to compare them.

Restored partial games with saved attempts or progress consume the start without
sending it again. Finishing one during the current visit can emit completion.
Transient selections and letters are not saved, so reloading after those actions
cannot identify an earlier start. Play again resets deduplication. Activity before
consent is never queued or replayed, and revoking consent stops events.
Measurement requires the production consent banner. An empty measurement ID or
staging pages without the banner emit no events, even with saved acceptance and
another `gtag` function present.

O piloto de feedback após uma partida concluída do quiz, sua configuração e rollback estão descritos em [Feedback do quiz](docs/feedback.md).

Photo downloads install complete responses atomically and keep a local `.sha256` sidecar. The download command reuses files only when their checksum matches; older files without a sidecar are downloaded once more.

To inspect run records left unfinished after an interruption, use `python -m kpop_scraping.recover_runs --database data/kpop.db`. This lists `running` records without writing; the database does not contain a heartbeat, so the list does not prove that a process has stopped. After checking that the process has stopped, close only its record with `--fail-run collection_runs:123` (replace the table and ID with the listed identity). Completed records and other running records are preserved; no age-based cleanup runs automatically.
